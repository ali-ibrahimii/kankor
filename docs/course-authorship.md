# نویسندهٔ کورس در پنل ادمین

کورسی که ادمین سایت می‌سازد متعلق به **پلتفرم** است، نه به شخص ادمین. یعنی روی
کارت کورس، صفحهٔ کورس و همهٔ فهرست‌ها نام «ابزار کانکور» دیده می‌شود، نه نام
شخصی کسی که در آن لحظه وارد شده است.

## چطور کار می‌کند

| مسیر | چه اتفاقی می‌افتد |
| --- | --- |
| **کورس‌های جدید** | `createCourse` با `platformAuthored: true` (فقط از پنل ادمین) فراخوانی می‌شود و `courses.instructor_id` را روی پروفایل پلتفرم می‌گذارد. |
| **کورس‌های قدیمی** | هر کورسی که نویسنده‌اش نقش `admin` دارد، در پنل با نام پلتفرم نمایش داده می‌شود (`markPlatformAuthors` + `usePlatformAuthors`). |
| **پروفایل پیدا نشد** | آرام برمی‌گردد به رفتار قبلی (ادمین نویسنده می‌ماند) — ساخت کورس هیچ‌وقت به‌خاطر این خطا شکست نمی‌خورد. |

## پیدا کردن پروفایل پلتفرم

`src/lib/platform-author.ts` به این ترتیب عمل می‌کند:

1. اگر `PLATFORM_AUTHOR_PROFILE_ID` در محیط ست شده باشد، همان id استفاده می‌شود.
2. در غیر این صورت بین پروفایل‌های با نقش `admin`، نامی که با برند یکی باشد
   («Abzar Kankor»، «ابزار کانکور») انتخاب می‌شود.
3. اگر هیچ‌کدام پیدا نشد → `null` و نویسنده همان ادمین می‌ماند.

نتیجه در هر درخواست یک‌بار و کش‌شده محاسبه می‌شود (`react/cache`).

### توصیه

برای اینکه رفتار قطعی و مستقل از نام پروفایل باشد، یک‌بار id پروفایل برند را
پیدا کنید و در `.env` بگذارید:

```sql
select id, full_name, role from public.profiles where role = 'admin';
```

```env
PLATFORM_AUTHOR_PROFILE_ID=<uuid>
```

## دسترسی‌ها (RLS)

هیچ policy جدیدی لازم نیست:

- **insert کورس:** ادمین با `is_admin()` اجازه دارد و می‌تواند `instructor_id`
  را روی پروفایل دیگری بگذارد (شرط policy: `instructor_id = auth.uid() OR is_admin()`).
- **update و محتوا:** `can_manage_course()` شامل `is_admin()` است، بنابراین ادمین
  همیشه می‌تواند ماژول/درس/بلاک کورس پلتفرم را ویرایش کند.
- **خواندن نقش پروفایل:** policy فعلی `profiles` اجازه می‌دهد هر کاربر احرازهویت‌شده
  ردیف‌های نقش `admin` را بخواند — همان چیزی که برای تشخیص نویسندهٔ پلتفرم لازم است.
